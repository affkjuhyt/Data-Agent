# REA phase R — OSS research: document intelligence for `worker_document`

Fetched 2026-11-12. Every claim cites the URL actually fetched; "not shown" = the page did not expose it. GitHub release pages show day/month only (footer © 2026). Nothing was run locally.

Our baseline: pdfminer.six + pypdfium2 + Pillow + tesseract (vie/eng), tables flattened to text before chunking, Điều/Khoản chunking with context header, bge-m3 via TEI → Qdrant, Postgres FTS, TEI cross-encoder rerank. One shared A100 40 GB already serving Qwen3-14B + 4B. PyMuPDF excluded (AGPL).

## 1. Docling — **Adopt (wrap as our PDF/scan backend)**

**Sources:** https://github.com/docling-project/docling (70.4k stars, 1,912 commits; "MIT license"; "hosted as a project in the LF AI & Data Foundation"; started by IBM Research Zurich) · https://github.com/docling-project/docling/releases (v2.150.0 10 Nov, v2.149.0 08 Nov, v2.148.0 05 Nov, v2.147.0 04 Nov, v2.146.0 03 Nov — ~10 releases 23 Oct→10 Nov) · https://raw.githubusercontent.com/docling-project/docling/main/pyproject.toml (`requires-python >=3.10,<4.0`, MIT) · https://docling-project.github.io/docling/getting_started/installation/ · https://arxiv.org/html/2408.09869v5 (technical report, v5 9 Dec 2024).

**Architecture.** `DocumentConverter` → format-specific backend → pipeline → `DoclingDocument`. PDF backends: `docling-parse` (default, better tables) or `pypdfium2` (faster, "worse quality results, especially in table structure recovery" — tech report §4). Standard PDF pipeline: layout model (RT-DETR-derived, trained on DocLayNet "among other proprietary datasets", 72 dpi, "sub-second latency" on one CPU) → TableFormer (ViT table-structure model; "Typical tables require between 2 and 6 seconds to be processed on a standard CPU") → OCR → reading-order assembly. Default layout spec is `DOCLING_LAYOUT_HERON` (Egret large/xlarge variants exist) — https://raw.githubusercontent.com/docling-project/docling/main/docling/datamodel/pipeline_options.py. Enrichments (all off by default, https://docling-project.github.io/docling/usage/enrichments/): code/formula (`ds4sd/CodeFormula`), picture classification (`docling-project/DocumentFigureClassifier-v2.5`), picture description via a VLM (SmolVLM-256M, Granite Vision 2B, or any OpenAI-compatible endpoint — we could point it at our vLLM). Alternative VLM pipeline: `granite_docling` (ibm-granite/granite-docling-258M, Apache-2.0, released 17 Sep 2025; languages "English", with Japanese/Arabic/Chinese "experimental" — **Vietnamese not mentioned**, https://huggingface.co/ibm-granite/granite-docling-258M). Granite-Docling FinTabNet 150 dpi TEDS: structure 0.97 / with content 0.96 (vs SmolDocling 0.82/0.76). SmolDocling paper (https://arxiv.org/html/2503.11576): 0.35 s/page on A100 with vLLM, 0.489 GB VRAM; TableFormer (52M) TEDS 0.89 FinTabNet / 0.84 PubTables-1M.

**Model weights.** `docling-tools models download` → `$HOME/.cache/docling/models`, `DOCLING_ARTIFACTS_PATH` for air-gapped (https://docling-project.github.io/docling/usage/advanced_options/). Hosted on HF: https://huggingface.co/docling-project/docling-models (layout + TableFormer; license tags cdla-permissive-2.0 and apache-2.0; TableFormer TEDS simple 95.4 / complex 90.1 / all 93.6 on the card). File sizes are not stated on the card.

**Speed (published).** Tech report Table 1 (225 pages, OCR off, GPU "largely untested"): Intel Xeon E5-2690, 4 threads: docling-parse 0.60 pages/s, 6.16 GB; 16 threads 0.92 pages/s; pypdfium 0.94 / 1.57 pages/s, 2.42 GB. Apple M3 Max: 1.27–2.45 pages/s. GPU page (https://docling-project.github.io/docling/usage/gpu/), ViDoRe V3 HR: standard pipeline no OCR 3.1 pages/s on L40S, 7.9 on RTX 5090 (CPU-only 1.5), with OCR 1.6 pages/s on 5090; `layout_batch_size`/`ocr_batch_size` default 4, "table_batch_size is currently not using GPU batching"; GraniteDocling via vLLM 2.4 pages/s on L40S. **Implication for us:** GPU is optional — CPU at ~1 page/s per 4 threads is usable for an ingest worker; the A100 does not need to be touched except for OCR batching.

**DoclingDocument** (https://docling-project.github.io/docling/concepts/docling_document/, docling-core source): pydantic model in `docling_core.types.doc`; top-level lists `texts`, `tables`, `pictures`, `key_value_items`; tree `body` (reading order = children order), `furniture` (deprecated → headers/footers now first/last in body), `groups`; `pages: dict[int, PageItem]` (`size`, `image`, `page_no`). Provenance per item: `ProvenanceItem(page_no: int, bbox: BoundingBox, charspan: CharSpan)` — https://raw.githubusercontent.com/docling-project/docling-core/main/docling_core/types/doc/common/reference.py. Tables — https://raw.githubusercontent.com/docling-project/docling-core/main/docling_core/types/doc/items/table/table_data.py: `TableCell(bbox: BoundingBox|None, row_span, col_span, start_row_offset_idx, end_row_offset_idx, start_col_offset_idx, end_col_offset_idx, text, column_header, row_header, row_section, fillable)`, `TableData(table_cells, num_rows, num_cols, grid)`. **This is exactly the "table as structure with cell provenance" we are missing.** Headings: `SectionHeaderItem.level`; by default the layout model does not know depth (all level 1); `HeadingHierarchyOptions(enabled=True, style_size_tolerance=0.05, max_level=6)` infers depth from PDF outline → numbering → font style, first applicable signal wins (https://docling-project.github.io/docling/usage/heading_levels/). Exports: Markdown, HTML, lossless JSON, DocTags, DocLang, chunks JSONL (https://docling-project.github.io/docling/usage/supported_formats/).

**Chunking** (https://docling-project.github.io/docling/concepts/chunking/, https://raw.githubusercontent.com/docling-project/docling-core/main/docling_core/transforms/chunker/hierarchical_chunker.py): `HierarchicalChunker` = one chunk per element, tables serialized by `TripletTableSerializer` (`"{row}, {col} = {value}"`), headings stack tracked per level (`heading_by_level`, shadowed deeper levels dropped), `DocMeta(doc_items=[… with prov], headings, origin)`. `HybridChunker` adds tokenizer-aware split/merge (`merge_peers`, `repeat_table_header=True`), `contextualize(chunk)` prepends headings for embedding. Our Điều/Khoản header approach maps naturally onto `headings` once legal numbering is detected as section headers.

**OCR** (https://docling-project.github.io/docling/concepts/OCR/, https://docling-project.github.io/docling/concepts/OCR_native/, pipeline_options.py): engines RapidOCR (default in `docling[standard]`), EasyOCR, tesserocr, tesseract-CLI, ocrmac, Nemotron-OCR (CUDA 13 only, no Vietnamese), KServe remote. `OcrOptions.lang` accepts native codes or `iso:` BCP-47; `OcrAutoOptions` picks first available, "Tesseract is never selected automatically". Vietnamese paths documented: RapidOCR PP-OCRv6 (`vi` listed; v4/v5 only "latin"), EasyOCR `latin_g2.pth` (~40 Latin codes incl. `vi`), Tesseract via `TesseractCliOcrOptions(lang=["vie","eng"])` — our existing tessdata keeps working. `OcrMode.FULL_PAGE` forces OCR; `replace_broken_text_layer` fixes PDFs with a garbage text layer (common in Vietnamese scans with bad embedded OCR).

**Dependency weight.** `pip install docling` = `docling-slim[standard]` → `models-local` (torch ≥2.2.2, torchvision, docling-ibm-models), docling-parse, RapidOCR/onnxruntime; CPU wheel via `--extra-index-url https://download.pytorch.org/whl/cpu`. docling-serve images: CPU 4.4 GB, cu128 11.4 GB (https://github.com/docling-project/docling-serve, MIT, 1.9k stars). Expect +~2–3 GB in the worker-document image (torch CPU + models).

**Integration complexity: 2/5.** Replace `pdfminer+pypdfium2+tesseract` extraction with `DocumentConverter(...).convert()`, keep our chunker but feed it `DoclingDocument` (tables → `TableItem.data.grid`, prov → page/bbox, headings from `SectionHeaderItem`). Vietnamese legal numbering (Điều/Khoản/Điểm) needs a custom numbering regex for `HeadingHierarchyOptions` or a post-pass; the layout model has no Vietnamese-specific training, so bake-off must check section-header detection on our docs.

**Do not copy:** the VLM pipeline (no Vietnamese, competes with our A100), picture description via SmolVLM/Granite Vision, `docling-serve` as a separate service (worker already owns the schema; call the library in-process), Markdown export as the retrieval unit (lossy — keep JSON).

## 2. docling-graph — **Reference (premature)**

https://github.com/docling-project/docling-graph : "Transform unstructured documents into validated, rich and queryable knowledge graphs." MIT, 943 stars, 519 commits, Python 3.10–3.12, LF AI & Data + OpenSSF badges; releases v1.9.2 08 Nov, v1.9.1/1.9.0/1.8.0 17 Jul (https://github.com/docling-project/docling-graph/releases). ## 3. Unstructured — **Reference / bake-off control; Reject as foundation**

**Sources:** https://github.com/Unstructured-IO/unstructured (15.7k stars, Apache-2.0, 2,034 commits) · https://raw.githubusercontent.com/Unstructured-IO/unstructured/main/pyproject.toml (`requires-python >=3.11,<3.14`, Apache-2.0; `pdf` extra = unstructured-inference ≥1.6.12, pdf2image, pdfminer.six, pikepdf, pypdf, unstructured-pytesseract, google-cloud-vision, pi-heif; `paddleocr` extra = paddlepaddle + unstructured-paddleocr 2.10.0; torch only in `huggingface` extra) · https://github.com/Unstructured-IO/unstructured/releases (0.27.37 Nov 6, 0.27.36 Oct 30, 0.27.35 Oct 27, 0.27.34/33 Oct 22, 0.27.32 Oct 20 — 9 releases in Oct) · https://github.com/Unstructured-IO/unstructured/commits/main (commits 6 Nov 2026: "chore: release 0.27.37", fixes to coordinates, pdf fast strategy, docx) — **actively maintained, bug-fix cadence.**

**Model and API.** `partition_pdf(strategy=auto|fast|hi_res|ocr_only)`: fast = pdfminer; hi_res = layout model from `unstructured-inference` (Apache-2.0, 210 stars) — `DEFAULT_MODEL = "yolox"` (`unstructuredio/yolo_x_layout/yolox_l0.05.onnx`, also `yolox_tiny`, `yolox_quantized`; detectron2_onnx) with 11 DocLayNet-style labels (https://raw.githubusercontent.com/Unstructured-IO/unstructured-inference/main/unstructured_inference/models/yolox.py); tables via `microsoft/table-transformer-structure-recognition` → `cells_to_html` (https://raw.githubusercontent.com/Unstructured-IO/unstructured-inference/main/unstructured_inference/models/tables.py); OCR tesseract (`languages=["vie","eng"]`) or paddle. Elements: Title, NarrativeText, ListItem, Table, Image, Header, Footer, Formula, FigureCaption, CodeSnippet, PageNumber, UncategorizedText…; metadata `page_number`, `coordinates` (points, system w/ layout width/height), `parent_id`, `category_depth`, `text_as_html` (tables only), `detection_class_prob`, `image_base64` (https://docs.unstructured.io/open-source/concepts/document-elements). Chunking: `basic`, `by_title` (`max_characters` 500, `new_after_n_chars`, `overlap`, `combine_text_under_n_chars`, `multipage_sections`); "A `Table` element is always isolated", oversized → `TableChunk`; `orig_elements` keeps page/coords (https://docs.unstructured.io/open-source/core-functionality/chunking).

**Commercial split** (https://docs.unstructured.io/open-source/introduction/overview): open source is "designed as a starting point for quick prototyping and has limits", "Not designed for production scenarios", "GPU usage is not supported for the Unstructured open source library", "No access to Unstructured's latest vision language model (VLM) offerings", no "fine-tuned OCR models", no by-page/by-similarity chunking, "Significantly decreased performance on document and table extraction", "Less sophisticated document hierarchy detection". README claims Transform v2 API text accuracy 0.878 vs 0.715 OSS. Library also sends telemetry by default (`DO_NOT_TRACK`).

**Table evidence vs Docling.** OmniDocBench v1.6 (https://raw.githubusercontent.com/opendatalab/OmniDocBench/main/README.md) lists Docling and Unstructured as evaluated tools but publishes **no results row for either**; pipeline rows: MinerU-Pipeline overall 86.47 / table TEDS 81.88, Marker 78.44 / 65.77. The only third-party head-to-head found: Tensorlake's vendor-run TEDS on 512 OmniDocBench tables, Marker 57.88 %, Docling 63.84 % (https://docs.tensorlake.ai/document-ingestion/production/benchmarks — vendor benchmark, treat as weak evidence). No published Unstructured-OSS TEDS found. Structural difference that matters more than scores: Unstructured gives tables as **HTML string** (`text_as_html`) with no per-cell bbox; Docling gives a typed cell grid with `TableCell.bbox` and spans. Table Transformer's own PubTables-1M heritage is solid, but hi_res has no GPU path in OSS.

**Integration complexity: 2/5** to call, **4/5** to get provenance-complete tables (parse HTML back to cells). Keep it as the bake-off control and as the fallback for DOCX/PPTX/EML if Docling's office backends fail on a format. Do not copy: `text_as_html` as the table representation, `by_title` chunking (character-based, English-centric Title heuristics), `strategy="auto"` (silently degrades to pdfminer, which is our current violation).

## 4. Microsoft GraphRAG — **Reject (Reference for the community-summary idea only)**

https://github.com/microsoft/graphrag : MIT, 36.6k stars; README: "GraphRAG indexing can be an expensive operation"; **"The project is in maintenance mode"** — no new PRs/features, bug fixes/CVE patches continue; "not an officially supported Microsoft offering". Releases v3.3.0 08 Oct, v3.2.0 24 Sep, v3.1.2 21 Aug (https://github.com/microsoft/graphrag/releases); `requires-python >=3.11,<3.14` (https://raw.githubusercontent.com/microsoft/graphrag/main/pyproject.toml).

**Cost model** (https://microsoft.github.io/graphrag/index/default_dataflow/, https://raw.githubusercontent.com/microsoft/graphrag/main/packages/graphrag/graphrag/config/defaults.py): text units of 1200 tokens / 100 overlap; **per text unit**: 1 entity+relationship extraction call + `max_gleanings=1` follow-up (so 2 LLM calls/chunk); **per entity and per relationship** with multiple descriptions: 1 summarization call (`max_length=500`); claims off by default; Leiden communities (`max_cluster_size=10`) then **per community per level**: 1 report call (`max_input_length=8000`, `max_length=2000`) + 1 short-summary call; then embeddings. For a 10k-chunk corpus that is ≥20k long-context generation calls before communities — on a shared A100 serving Qwen3-14B this is days of GPU time per re-index, and re-index on every document version (our `available_at` point-in-time rule) multiplies it. Query: local (entities + text chunks), global ("map-reduce" over community reports, "resource-intensive"), DRIFT, basic (https://microsoft.github.io/graphrag/query/overview/). **LazyGraphRAG:** announced Nov 2024 as "0.1 % of full GraphRAG indexing cost"; as of this fetch the README, config docs and dataflow docs contain no "lazy" mention; Microsoft's project page offers it through Microsoft Discovery (hosted). Not available to us in OSS — unverified beyond that.

Lighter alternatives: **LightRAG** (https://github.com/HKUDS/LightRAG, MIT, 40.7k stars, v1.5.7 02 Sep, Python ≥3.10, supports Postgres for all four stores + Qdrant + bge-m3 + bge-reranker-v2-m3 — matches our stack, but still an extraction LLM call per chunk; its server ships with auth off). **nano-graphrag** (https://github.com/gusye1234/nano-graphrag, MIT, 4.0k stars, "about 1100 lines of code", 155 commits, no release dates visible — study copy, not a dependency). Verdict for on-prem limited GPU: Reject graph indexing now; our semantic model + SQL already is the structured graph for data questions; revisit LightRAG if cross-document entity questions appear in eval sets.

## 5. LlamaIndex — **Extract (ideas), not Adopt**

https://github.com/run-llama/llama_index : MIT, 52.9k stars, 7,967 commits; `llama-index-core` 0.14.25 (21 Sep 2026; 0.14.24 19 Aug, 0.14.23 24 Jun — https://github.com/run-llama/llama_index/releases), `requires-python >=3.10,<4.0`, 29 runtime deps incl. nltk, tiktoken, SQLAlchemy, numpy, no torch (https://raw.githubusercontent.com/run-llama/llama_index/main/llama-index-core/pyproject.toml). "over 300 LlamaIndex integration packages". Commercial: "LlamaParse — our enterprise platform for agentic OCR, parsing, extraction, indexing" (Parse/Extract/Index/Split/Agents); the OSS framework is usable without it.

What we would use (https://developers.llamaindex.ai/python/framework/module_guides/loading/node_parsers/modules/): `SentenceWindowNodeParser` (window_size=3, window in metadata, swapped in by `MetadataReplacementNodePostProcessor`), `HierarchicalNodeParser` (chunk_sizes [2048, 512, 128], parent refs) + `AutoMergingRetriever` (leaf nodes in the vector index, all nodes in a docstore, "recursively merges subsets of leaf nodes that reference a parent node beyond a given threshold" — the example shows 6 retrieved → 3 after merge, pairwise preference ≈0.525, i.e. marginal gain; https://developers.llamaindex.ai/python/examples/retrievers/auto_merging_retriever/), `SemanticSplitterNodeParser` ("regex primarily works for English sentences" — not for Vietnamese), `DoclingReader`/`DoclingNodeParser` (`llama-index-readers-docling`, `llama-index-node-parser-docling`, https://docling-project.github.io/docling/integrations/llamaindex/). `SQLJoinQueryEngine` (https://developers.llamaindex.ai/python/examples/query_engine/sqljoinqueryengine/): selector picks SQL tool → runs NL-to-SQL → "Transformed query given SQL response" → second engine → synthesis; `SQLAutoVectorQueryEngine` is the older subclass. This is a two-hop router with an LLM-written SQL — it violates our invariant 15/16 (output contract before execution, governed SQL); our agentic engine already does the planning.

**Integration complexity: 4/5** (its Node/Document/ServiceContext objects would wrap everything: embeddings, vector store, LLM). Extract: the parent/child node ids with `simple` ratio merge (store `parent_chunk_id` in Qdrant payload, merge in our retriever), sentence-window metadata replacement for Khoản-level chunks. Do not copy: query engines, `SemanticSplitter`, any dependency on `llama-index` packages.

## 6. Haystack 2.x — **Reference**

https://github.com/deepset-ai/haystack : Apache-2.0, ~27.0k stars, 6,808 commits; v3.5.0 10 Nov, v2.31.1 03 Nov (https://github.com/deepset-ai/haystack/releases; `VERSION.txt` = 3.6.0-rc0), `requires-python >=3.11`, 20 base deps, no torch/pandas (https://raw.githubusercontent.com/deepset-ai/haystack/main/pyproject.toml). Pipelines of components with "loops, branches, and conditional logic", sync/async. Commercial: "Haystack Enterprise Platform" (managed/self-hosted) — the OSS is complete for our needs. Components we'd use: `DoclingConverter` (`docling-haystack`, "Maintained by deepset", export `DOC_CHUNKS` default | `MARKDOWN` | `JSON`, pluggable Docling `chunker`; https://haystack.deepset.ai/integrations/docling), `DocumentSplitter` (`split_by` word/sentence/passage/page/line/period/token/function, overlap, threshold; adds `source_id`, `page_number`), `RecursiveDocumentSplitter`, `HierarchicalDocumentSplitter` (https://docs.haystack.deepset.ai/docs/documentsplitter), Qdrant retriever, TEI/SentenceTransformers rankers. Verdict: pipeline abstraction buys us nothing (worker already has an outbox-driven pipeline) and would double-wrap TEI/Qdrant; `split_by="function"` is the pattern to copy for Điều/Khoản. Complexity 3/5. Do not copy: its Document store abstractions, the pipeline YAML.

## Proposed bake-off protocol

**Corpus (30 docs, ours):** 10 Vietnamese legal/regulatory PDFs with native text (Điều/Khoản, multi-column where available, ≥1 table each), 8 scanned Vietnamese administrative/legal PDFs (300 dpi + 2 phone scans), 6 financial reports (3 Vietnamese, 3 FinTabNet pages as external sanity check), 3 DOCX, 3 mixed/rotated pages. Ground truth: tables hand-labelled to the FinTabNet cell schema (row/col index, span, text) in a `tests/data` fixture; reading order as the human-ordered list of blocks; OCR text transcribed for the 8 scans (sample ≥5 pages each); heading tree (Chương/Điều/Khoản) per doc.

**Systems:** (A) current pipeline (pdfminer.six + pypdfium2 + tesseract vie), (B) Docling standard pipeline, docling-parse backend, TableFormer ACCURATE, `HeadingHierarchyOptions(enabled=True)`, OCR variants B1 TesseractCli `vie,eng` / B2 RapidOCR PP-OCRv6 `vi`, CPU 4 threads and CUDA on the A100 (layout/OCR batch 16), (C) Unstructured `hi_res`, yolox, `infer_table_structure=True`, `languages=["vie","eng"]`, CPU.

**Metrics:** table TEDS and TEDS-S (OmniDocBench's evaluator code, Apache-2.0) plus cell F1 (exact text, row/col match); reading-order normalized edit distance over block sequence (OmniDocBench metric); OCR CER/WER with diacritics (NFC-normalized) and a second CER with diacritics stripped to isolate diacritic loss; heading F1 (Điều/Khoản detected with correct level); wall time per page CPU and GPU, peak RSS/VRAM; image size delta.

**Pass bar to replace the current pipeline:** table cell F1 ≥ 0.85 on native-text PDFs and ≥ 0.70 on scans, reading-order ED ≤ 0.10, Vietnamese CER no worse than current Tesseract, ≤ 3 s/page CPU median. Run as a `make` target in the worker-document image, results committed under `model/eval/` with the same report format as `eval-retrieval`.

**Known evidence gaps:** no public Docling or Unstructured row on OmniDocBench; no published Vietnamese CER for PaddleOCR/RapidOCR; Docling's layout model has no Vietnamese training claim; UIT-DODV license unknown.
