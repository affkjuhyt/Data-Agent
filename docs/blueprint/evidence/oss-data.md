## 1. dlt (dlt-hub/dlt)

**Fetched:** https://github.com/dlt-hub/dlt (6.1k stars, "released under the Apache 2.0 License", Python 3.10–3.14), https://raw.githubusercontent.com/dlt-hub/dlt/devel/LICENSE.txt (Apache-2.0 verbatim), https://pypi.org/project/dlt/ (1.32.0, 29 Oct 2026, `>=3.10,<3.15`), https://github.com/dlt-hub/dlt/releases (1.32.0 29 Oct, 1.31.0 7 Oct, 1.30.0 11 Aug, 1.29.1 24 Jul — roughly monthly), https://github.com/dlt-hub/dlt/commits/devel (last commit 11 Nov 2026), https://github.com/dlt-hub/dlt/tree/devel/dlt (package layout), docs: schema-contracts, incremental-loading, incremental/cursor, state, sql_database (+configuration), rest_api/basic, destination, plus/intro.

**Architecture (paths under `dlt/`):** `extract/` (sources = decorated generators, resources), `normalize/` (nested-JSON flattening, schema inference, `_dlt_id`/`_dlt_parent_id` child tables), `load/` (load packages identified by `load_id`, written to `_dlt_loads`; rows whose load_id is missing from `_dlt_loads` are incomplete loads), `destinations/` (20+: postgres, duckdb, filesystem/Parquet with a DuckDB SQL client over the files, mssql, snowflake…), `sources/` (`sql_database`, `rest_api`, `filesystem`), `pipeline/`, `common/`. State lives in the pipeline working dir **and** in `_dlt_pipeline_state` at the destination; it is restored from the destination on a clean start (keyed by pipeline name + destination + dataset). Schema contracts: per `tables` / `columns` / `data_type`, modes `evolve` (default) / `freeze` (raises `DataValidationError` inside `PipelineStepFailed`) / `discard_row` / `discard_value`; a Pydantic model passed as `columns` sets the contract. Incremental: `dlt.sources.incremental(cursor_path, initial_value, end_value, last_value_func=max, row_order, range_start="closed", range_end="open")`; dedup of overlapping rows by `primary_key` or content hash; `end_value` runs are stateless backfills. `sql_database`: any SQLAlchemy dialect; backends `sqlalchemy` (dicts, slowest), `pyarrow` (Arrow tables, exact decimals, skips normalizer when destination loads Parquet, "20x–30x" faster per docs), `pandas` (lossy, discouraged), `connectorx` (fastest, only validated on PostgreSQL, ignores `chunk_size`); incremental pushes `WHERE cursor >= :start` into the reflected query; `reflection_level=full_with_precision`; `table_adapter_callback`. `rest_api`: declarative `RESTAPIConfig` (`client`, `resource_defaults`, `resources[]` with `endpoint.path/params/paginator/data_selector/incremental`), paginators `json_link/header_link/header_cursor/offset/page_number/cursor/single_page/auto`, auth `bearer/http_basic/api_key/oauth2_client_credentials`, parent→child via `{resources.parent.field}` placeholders, `processing_steps` filter/map.

**Commercial split:** the library is Apache-2.0; "dltHub" (AI Harness, managed deployment/scheduling, workspace dashboard, premium destinations: Iceberg, Delta, Snowflake Plus, **MS SQL with change tracking**) is under a commercial "dltHub License" (https://dlthub.com/docs/plus/intro). Note: SQL Server change-tracking CDC is on the paid side.

**Technique that solves our problem:** the cursor/boundary/dedup contract (`range_start` closed, `range_end` open, backfill with fixed `end_value`), the load-package/`_dlt_loads` completeness marker, and schema contracts with `discard_value` for variant columns. These are exactly the semantics our hand-written cursor incremental lacks a formal spec for.

**Could dlt replace worker_ingest drivers?** Technically yes for Postgres/MySQL/SQL Server (SQLAlchemy dialects) and ClickHouse (community dialect, unvalidated). What we would lose or have to re-build:
- **RLS-scoped writes**: dlt's postgres destination writes with its own connection/credentials and owns the tables (`_dlt_*` columns, naming convention, its own DDL with `ALTER TABLE` on evolve). Our workspace tables are RLS-scoped per org; dlt would have to write into a per-org schema with a role we set up, or we post-process. No hook for `SET ROLE`/`set_config` per load.
- **OpenBao `secret_ref`**: dlt resolves credentials through its config providers (toml/env/`dlt.secrets`); we would write a provider that resolves `secret_ref` at run time — feasible but a custom provider.
- **Our job/run tables**: dlt keeps state in `_dlt_pipeline_state`; we would keep our `ingest.job/run` as the system of record and store dlt's state blob ourselves (dlt docs allow disabling `restore_from_destination`).
- Normalizer renames columns (snake_case naming convention) and adds `_dlt_id/_dlt_load_id`; our profiler/quality SQL assumes source column names.

**Maturity:** active (monthly minors, commit 11 Nov 2026). **Integration complexity: 3** for `sql_database`-as-engine behind our driver interface; **4** if we let dlt own the destination tables.
**Recommendation: Extract (cursor/boundary/dedup/contract semantics, load-package completeness marker) + Wrap `rest_api` only** when SaaS sources arrive — the paginator/auth/placeholder config is a solved problem we should not rewrite. **Do not copy:** the normalizer's child-table flattening and `_dlt_*` columns (structured data must stay structured, invariant), its toml/env secrets model, its destination-owned DDL.

## 3. DuckDB

**Fetched:** https://github.com/duckdb/duckdb (43.0k stars, MIT, C++17), https://github.com/duckdb/duckdb/releases (v2.0.0 "Cyanoptera" 21 Oct 2026; v1.5.6 28 Sep; v1.5.5 22 Jul; v1.5.4 17 Jun), https://duckdb.org/2026/10/21/announcing-duckdb-200, https://duckdb.org/docs/2.0/clients/python/overview.html, https://duckdb.org/docs/2.0/core_extensions/postgres/overview.html, https://duckdb.org/docs/2.0/configuration/overview.html, https://duckdb.org/docs/2.0/operations_manual/securing_duckdb/overview.html.

**Key facts:** 2.0 is an **LTS until at least Oct 2027**; 1.4 LTS supported until 17 Nov 2026, 1.5 until Mar 2027. Breaking in 2.0: PEG parser default (`legacy_parser` extension), single-arrow lambdas off (removed in 2.1), ICU moved to extension; pre-2.0 DuckDB cannot read 2.0 files unless `storage_compatibility_version='v1.5.0'`; 2.0 reads old files. Python client **requires Python ≥ 3.11** (ours), no free-threaded builds; `duckdb.connect()`/`cursor()` per thread; queries pandas/Polars/PyArrow objects by variable name (replacement scans, read-only); `.df()/.pl()/.to_arrow_table()/.to_arrow_reader()/.fetchnumpy()`. **Config defaults:** `memory_limit` = 80 % of RAM, `threads` = #cores, `max_temp_directory_size` = 90 % of disk, `enable_external_access=true`, `autoinstall_known_extensions=true`, `lock_configuration=false`. **Securing for untrusted SQL** (the doc's own words: "Treat SQL in DuckDB like code in Bash or Python… Do not execute SQL from untrusted sources without proper sandboxing"): in order, `SET enable_external_access=false; SET disabled_filesystems='LocalFileSystem'; SET autoload_known_extensions=false; SET autoinstall_known_extensions=false; SET allow_community_extensions=false; SET memory_limit/threads/max_temp_directory_size; SET lock_configuration=true` (with `allowed_configs` for the few we want tunable); timeouts are **application-level** (no query timeout setting). **postgres extension:** `ATTACH 'dsn' AS pg (TYPE postgres, READ_ONLY, SCHEMA 'x')`, reads via binary `COPY` (`pg_use_binary_copy=true`), filter pushdown (`pg_enable_filter_pushdown=true`), ctid-parallel scans (`pg_pages_per_task=1000`), `pg_statement_timeout_millis`, NUMERIC>38 as VARCHAR option, schema cache (`postgres_clear_cache()`), `postgres_query(db, sql)`; 2.0 adds `CONNECT` to push a whole session down; warns not to put passwords in the DSN (use secrets).

**Where it fits for us:** (a) sandbox computation — replace ad-hoc pandas joins with SQL over Arrow/Parquet in-process, hard-capped by `memory_limit`/`threads`; (b) cross-source joins — attach the Postgres workspace read-only plus Parquet snapshots from MinIO (httpfs/S3 extension needs `enable_external_access=true`, so load extensions first, then lock); (c) Parquet snapshots for reproducibility — `COPY (…) TO 's3://…/snap.parquet'` with DuckDB or pyarrow (§5).
**Maturity:** very high; weekly-to-monthly patches, LTS lines. **Integration complexity: 2** (pip wheel, no service). **Recommendation: Adopt** in the sandbox pod and in worker_agent for snapshot/cross-source reads, pinned to the 2.0 LTS line; apply the securing checklist at connection open and run it only inside the no-egress pod. **Do not copy:** letting the agent `ATTACH` live sources directly (keeps RLS and query-in-place invariants intact only if reads go through our Postgres workspace or immutable Parquet).

## 4. SQLGlot

**Fetched:** https://github.com/tobymao/sqlglot (9.8k stars, MIT, "no-dependency SQL parser, transpiler, optimizer, and engine"; official dialects incl. ClickHouse, DuckDB, MySQL, Postgres, TSQL; community incl. Doris, Materialize; `sqlglot[c]` mypyc build ~3–5× faster), https://github.com/tobymao/sqlglot/blob/main/README.md, https://github.com/tobymao/sqlglot/tags (v30.31.0 10 Nov; 30.30.0 6 Nov; 30.29.0 3 Nov; 30.28.0 2 Nov; 30.27.0 30 Oct — several minors per week), https://pypi.org/project/sqlglot/ (30.31.0, 10 Nov 2026, `>=3.9`; **25.24.5 released 8 Oct 2024**), https://sqlglot.com/sqlglot/lineage.html, https://raw.githubusercontent.com/tobymao/sqlglot/main/sqlglot/optimizer/qualify.py. **Not fetched:** releases page (empty — project uses tags), CHANGELOG (2.1 MB, GitHub refuses to render).

**Our pin is 25 months and five majors behind** (25 → 30). SQLGlot bumps the major on any breaking AST change, so the gap is mostly accumulated dialect fixes plus renamed/removed expression classes; budget a day for the upgrade and run our sqlgen/sql_guard tests.

**Modules for our problems:** `sqlglot.lineage.lineage(column, sql, schema=, sources=, dialect=)` → `Node(name, expression, source, downstream, source_name, reference_node_name, payload)`; qualifies, walks scopes through CTEs/subqueries/set ops/pivots, `*` expansion needs schema, unresolvable columns become `Placeholder` leaves (column-level lineage for our catalog without a second engine). `sqlglot.optimizer.qualify.qualify(expr, schema=, db=, catalog=, qualify_columns=True, validate_qualify_columns=True, quote_identifiers=True, allow_partial_qualification=False, on_qualify=cb)` — the right place to enforce "every table resolved against the allowed catalogue" (`on_qualify` callback) and "every column exists" (raises on unknown columns). **Read-only enforcement pattern:** parse with `error_level=RAISE`, reject if root is not `exp.Select/Union/With`, walk for `exp.Insert/Update/Delete/Merge/Create/Drop/Alter/Command/Set/Transaction`, reject `exp.Anonymous` functions not on an allow-list, and reject `exp.Into`/`exp.Copy`; then `qualify()` with the catalogue schema so unknown tables fail before execution. Caveats the README states: parser "is intentionally lenient… a transpiler, not a validator" — a parse is not a proof of validity, so execute under a read-only role/transaction too; `sqlglot[c]` disables runtime subclassing of dialects; comments best-effort; executor is for tests only.
**Integration complexity: 1** (already a dependency). **Recommendation: Adopt (already) — upgrade to 30.x, and add lineage + qualify-with-schema** to sql_guard and the catalog. **Do not copy:** the `executor`; do not rely on sqlglot alone for safety (defense in depth with DB role + statement_timeout + read-only transaction).

## 8. LangGraph vs pydantic-graph

**Fetched:** https://github.com/langchain-ai/langgraph (44.8k stars, MIT), https://pypi.org/project/langgraph/ (1.2.20, 5 Nov 2026, `>=3.10`, MIT), https://github.com/langchain-ai/langgraph/tree/main/libs/checkpoint-postgres (MIT, psycopg 3, `PostgresSaver.from_conn_string(uri)` → `.setup()` creates tables, `AsyncPostgresSaver`; requires `autocommit=True`, `row_factory=dict_row`; `LANGGRAPH_STRICT_MSGPACK=true` to restrict deserialisation), https://docs.langchain.com/oss/python/langgraph/interrupts (`interrupt(value)` pauses, `Command(resume=…)` resumes under the same `thread_id`; **the node re-runs from its start on resume**, so code before `interrupt()` must be idempotent; interrupts matched by index; `interrupt_before/after` are for debugging), https://docs.langchain.com/oss/python/langgraph/persistence (checkpointers = thread-scoped state; stores = cross-thread; thread_id <255 chars on Postgres; checkpoints grow unbounded — retention needed; subgraphs have their own namespace), https://docs.langchain.com/langsmith/self-hosted ("Self-hosted LangSmith is an add-on to the Enterprise plan"; needs Postgres + Redis + ClickHouse (or SmithDB on PG18+) + object storage; licence key from sales). **Not fetched:** the durable-execution page (every URL variant redirected to the persistence overview), PyPI page for `langgraph-checkpoint-postgres` (site error).
**pydantic-graph:** https://pypi.org/project/pydantic-graph/ (2.67.0, 11 Nov 2026, `>=3.11`, MIT, "developed as part of Pydantic AI but with no dependency on it"), https://pydantic.dev/docs/ai/graph/graph/ and /graph/ index (`GraphBuilder` → `g.node()`/edges → `g.build()`; `BaseNode.run(ctx: GraphRunContext)` with return type as edges, `End`, `deps_type`, `graph.iter()` for step-by-step with override of the next step, `graph.render()` Mermaid; docs say to use graphs "only when control flow is the hard part"). **Not fetched:** a persistence page (404 at the guessed path; the index lists only `builder/` and `builder/steps/`), so `FileStatePersistence`/`FullStatePersistence` could not be confirmed in the current 2.x docs.

**Comparison for us:** our plan DAG is statically validated before execution (invariant 17) and runs under Temporal for durability. LangGraph's value is runtime checkpoint-per-superstep + `interrupt()`; its costs are a second persistence layer in Postgres (own tables, msgpack blobs, retention policy, no RLS awareness), the resume-re-executes-node rule, and the LangChain message/state conventions leaking into our agent core. Temporal already gives durable execution, retries, signals (= human-in-the-loop) and schedules, and pydantic-ai 2.x already exposes `pydantic-graph` for explicit state machines. The commercial split (LangSmith Deployment/Platform, Enterprise-only self-host) does not touch the MIT library but shows where the vendor's roadmap goes.
**Complexity:** LangGraph 4 (new state/persistence model across the agent core); pydantic-graph 2 (same vendor, same Python ≥3.11, same typing idiom). **Recommendation: Reject LangGraph; Extract** its two good ideas — `interrupt()`-style typed pause values with a response schema, and a checkpoint retention policy — into our Temporal-backed plan runner; **Reference** pydantic-graph's `GraphBuilder` if we ever want our DAG executed as typed nodes rather than hand-rolled. **Do not copy:** LangGraph's checkpoint tables, msgpack state, LangChain message types.

## 9. Code sandbox: E2B and self-hosted alternatives

**Fetched:** https://github.com/e2b-dev/E2B (14.8k stars, Apache-2.0; SDKs/CLI repo), https://github.com/e2b-dev/infra (Apache-2.0, "The runtime needs Linux with KVM", Firecracker microVMs, Postgres + Redis + ClickHouse + object storage; Terraform for GCP/AWS/Azure or Kubernetes manifest; "E2B Embed is the whole stack… on a single Linux host with KVM"; "Embed is one machine by design"), https://docs.e2b.dev/self-hosting (Embed Apache-2.0, single machine incl. "a node in your Kubernetes cluster"; multi-node = BYOC, Enterprise-only), https://github.com/google/gvisor (20.0k stars, Apache-2.0, "Application Kernel for Containers", `runsc` integrates with Docker and Kubernetes), https://github.com/google/gvisor/releases (release-20261102.0, 20261026.0, 20261019.0 — weekly), https://gvisor.dev/docs/architecture_guide/platforms/ (systrap default since mid-2023 and recommended inside VMs; KVM fastest on bare metal; ptrace unsupported), https://gvisor.dev/docs/user_guide/containerd/quick_start/ (containerd ≥1.3.9/1.4.3, `runtime_type="io.containerd.runsc.v1"`, `RuntimeClass{handler: runsc}` → `runtimeClassName: gvisor`), https://github.com/kata-containers/kata-containers (9.1k, Apache-2.0, needs VT-x/AMD-V; 4.3.1 on 21 Oct 2026), https://github.com/microsandbox/microsandbox (9.0k, Apache-2.0, "still beta software. Expect breaking changes", KVM on Linux), https://github.com/engineer-man/piston (2.8k, MIT, Isolate in Docker: namespaces+chroot+cgroups, 3 s CPU/wall default), https://github.com/google/nsjail (4.2k, Apache-2.0, namespaces + cgroups v1/v2 + rlimits + Kafel seccomp-bpf, no releases).

**Assessment:** E2B's SDK and infra are both Apache-2.0 (no licence problem), but the runtime is Firecracker-on-KVM with its own control plane and four backing services; the open-source path is one Linux host ("Embed"), multi-node is Enterprise. On k3s on-prem that means a dedicated KVM node outside the cluster's scheduling model and a second Postgres/ClickHouse/Redis — too heavy for a sandbox we already have. Kata gives VM isolation inside k8s but needs hardware virt on every sandbox node (nested virt if k3s nodes are VMs, with the performance penalty gVisor's own docs describe). microsandbox is beta; Piston/nsjail are process jails for compile-and-run, not pod runtimes, and would replace rather than harden our pod.
**gVisor RuntimeClass is the pragmatic hardening:** it is a containerd runtime handler (k3s ships containerd), one DaemonSet/node-prep step to install `runsc` + shim, one `RuntimeClass`, one line in the sandbox pod spec; systrap works in VMs without nested virt; weekly releases. It keeps our existing NetworkPolicy no-egress, read-only root fs and non-root user, and adds a syscall-level kernel boundary — the layer the DuckDB security doc asks for ("isolated containers with restricted capabilities… OS-level sandboxing"). Cost: syscall-heavy pandas I/O is slower; no GPU; some pyarrow mmap paths may need testing.
**Complexity:** gVisor 2; Kata 3; E2B 5. **Recommendation: Adopt gVisor RuntimeClass** for the sandbox pod (and later for any DuckDB-over-untrusted-SQL worker); **Reject** E2B self-host, microsandbox, Piston; **Reference** Kata as the step-up if a customer demands VM isolation; **Extract** Piston's default limits (CPU-time + wall-time cap, process cap, per-run unprivileged user) into our pod spec. **Do not copy:** E2B's template/snapshot service — our sandbox is stateless per run by design.
