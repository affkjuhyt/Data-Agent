## 1. eosphoros-ai/DB-GPT

**Scope & architecture.** "Open-source agentic AI data assistant" (README, https://github.com/eosphoros-ai/DB-GPT). uv workspace of packages `dbgpt-core`, `dbgpt-app`, `dbgpt-serve`, `dbgpt-ext`, `dbgpt-client`, `dbgpt-sandbox`, `dbgpt-accelerator/*`; version 0.8.2, `requires-python >= 3.10`, no top-level deps (per-package) (https://raw.githubusercontent.com/eosphoros-ai/DB-GPT/main/pyproject.toml). AWEL is a DAG workflow runtime: `BaseOperator(DAGNode, ABC, Generic[OUT], metaclass=BaseOperatorMeta)` with `_do_run`, `call`/`call_stream`, a `WorkflowRunner.execute_workflow`, a `ContextVar` DAG context and streaming flags `streaming_operator`/`incremental_output` (https://raw.githubusercontent.com/eosphoros-ai/DB-GPT/main/packages/dbgpt-core/src/dbgpt/core/awel/operators/base.py). Multi-agent lives in `packages/dbgpt-core/src/dbgpt/agent/{core,expand,middleware,resource,skill,claude_skill,util}` (tree page fetched; file contents not). Text2SQL is the "chat_db" scene; fine-tuning is the separate DB-GPT-Hub project. The web UI (Next 16.3.8 / React 18) depends on `@antv/gpt-vis ^0.0.5`, `@antv/ava`, `@antv/g2`, `@ant-design/plots` (https://raw.githubusercontent.com/eosphoros-ai/DB-GPT/main/web/package.json). GPT-Vis itself is AntV's MIT library (801 stars, 26 chart types, a ```` ```vis ```` markdown DSL; https://github.com/antvis/GPT-Vis).

**Key modules.**
- Schema linking: `packages/dbgpt-serve/src/dbgpt_serve/datasource/service/db_summary_client.py` — `get_db_summary(dbname, query, topk)` builds `DBSchemaRetriever(top_k, table_vector_store_connector, field_vector_store_connector, separator="--table-field-separator--")` over two vector collections `<db>_profile` and `<db>_profile_field`, populated by `DBSchemaAssembler` + `RDBTextSplitter`; the prompt receives `[d.content for d in table_docs]`.
- Generation: `packages/dbgpt-app/src/dbgpt_app/scene/chat_db/auto_execute/chat.py` (`ChatWithDbAutoExecute`) — retrieval with fallback to `table_simple_info` truncated to `schema_max_tokens` (a TODO notes it counts characters, not tokens); no few-shot examples.
- Prompt: `.../auto_execute/prompt.py` — "You are a database expert", JSON with `thoughts`, `direct_response`, `sql`, `display_type`; rules: "grammatically correct {dialect} sql", "limit the query to a maximum of {top_k} results", "only use the tables provided".
- Output/validation: `.../auto_execute/out_parser.py` — the only SQL check is `sqlparse` statement type != UNKNOWN (no statement-type restriction); execution is a callable returning a DataFrame; vector columns reduced with sklearn PCA for `response_vector_chart`; `thoughts = dict` default bug.
- Chart selection: `packages/dbgpt-core/src/dbgpt/vis/tags/vis_chart.py` — LLM picks from 8 names (`response_line_chart`, `response_pie_chart`, `response_table`, `response_scatter_chart`, `response_bubble_chart`, `response_donut_chart`, `response_area_chart`, `response_heatmap`) via `default_chart_type_prompt()`.

**Maturity.** 20,288 stars; API `open_issues_count` 507 (web: 392 issues, 115 PRs); `pushed_at` 2026-11-11 (https://api.github.com/repos/eosphoros-ai/DB-GPT). Releases: v0.8.2 2026-08-26, v0.8.1 18 Jun, v0.8.0 27 Mar, v0.7.5 11 Feb — roughly quarterly (https://github.com/eosphoros-ai/DB-GPT/releases, https://api.github.com/repos/eosphoros-ai/DB-GPT/releases/latest). v0.8.2 notes list security fixes (Jinja2 sandbox escape/RCE, path traversal in upload, command injection, CORS) — a signal about the baseline.

**License / commercial.** MIT, "Copyright (c) 2023 magic.chen" (https://raw.githubusercontent.com/eosphoros-ai/DB-GPT/main/LICENSE). No commercial edition found on the README.

**Technique that solves one of our problems.** Two-level (table + field) schema retrieval with a top-k retriever is a clean pattern for schema linking on wide schemas; the chart-type enum chosen by the LLM alongside the SQL is a cheap, reliable chart-gen contract.

**Integration complexity: 4/5.** Monolithic app with its own serve layer, storage manager, vector stores and AWEL runtime; nothing is importable without most of the platform. **Recommendation: Reference.** Read `db_summary_client.py`/`vis_chart.py` for the pattern; do not depend on the packages. **Do not copy:** the output parser (sqlparse-only "validation", no statement whitelist, string truncation instead of token budget), the 8-chart enum as-is (we already have a chart contract), the AWEL runtime (pydantic-ai covers it).

## 2. Canner/WrenAI

**Scope & architecture.** Restructured in 2026: "On 2026-05-07 Wren Engine merged into this repo under `core/`"; the old chat-first product is "Wren GenBI Classic" on branch `legacy/v1`, tag `v1-final`, "no new features or security fixes" (https://raw.githubusercontent.com/Canner/WrenAI/main/README.md). Layout: `core/wren-core` (Rust semantic engine, Apache DataFusion-based), `core/wren-core-base`, `core/wren-core-py` (PyO3/maturin bindings), `core/wren-core-wasm`, `core/wren` (Python SDK + CLI `wrenai`), `core/wren-mdl` (`mdl.schema.json`); `sdk/wren-langchain`, `sdk/wren-pydantic`; `skills/`; `docs/`; `examples/`; `evals/spodbtify_ab` (tree only, no README visible). The Python package: `wrenai` 0.18.0, `requires-python >= 3.11`, Apache-2.0, deps `wren-core-py>=0.8.2`, `duckdb>=1.5`, `sqlglot>=29`, `pydantic>=2`, `pyarrow`, `pandas`; extras per warehouse, `memory` (LanceDB + sentence-transformers or ONNX), `mcp` (https://raw.githubusercontent.com/Canner/WrenAI/main/core/wren/pyproject.toml).

**Key modules / what is reusable.**
- *MDL schema* (https://raw.githubusercontent.com/Canner/WrenAI/main/core/wren-mdl/mdl.schema.json): manifest requires `catalog`, `schema`; arrays `models`, `relationships`, `cubes`, `views`, `enumDefinitions`; `dataSource` enum (BIGQUERY, POSTGRES, SNOWFLAKE, DUCKDB, DATABRICKS, …). Model: `name`, one of `tableReference`/`refSql`(WIP)/`baseObject`(WIP), `columns[{name,type,expression,isCalculated,relationship,notNull,isHidden,columnLevelAccessControl,properties}]`, `primaryKey`, `uniqueKeys`, `rowLevelAccessControls[{name,requiredProperties,condition}]`. Relationship: `models` (exactly two), `joinType ∈ {ONE_TO_ONE, ONE_TO_MANY, MANY_TO_ONE, MANY_TO_MANY}`, `condition`. Cube: `baseObject`, `measures[{name,expression,type}]`, `dimensions`, `timeDimensions`, `hierarchies`. View: `name`, `statement`. There is **no** top-level `metrics` or `timeGrain` — cubes replace them and grain is a query-time flag. Shape is close to our MetricFlow-shaped YAML (`semantic_yaml.py`); the differences are relationships as first-class objects with cardinality, and RLS/CLS rules inside the model.
- *Semantic → SQL compiler*: Rust (`core/wren-core`, DataFusion), exposed through `wren-core-py`: `SessionContext(mdl_base64)`, `transform_sql(sql) -> planned SQL`, `dry_run` (EXPLAIN, no execution), `register_parquet/csv`, `query -> Arrow IPC`; Python ≥ 3.11, prebuilt wheels for Linux/macOS/Windows (https://raw.githubusercontent.com/Canner/WrenAI/main/core/wren-core-py/README.md). The CLI adds `strict_mode` ("rejects queries referencing tables not defined in the MDL") and `denied_functions` (https://raw.githubusercontent.com/Canner/WrenAI/main/core/wren/README.md).
- *pydantic-ai adapter* (https://github.com/Canner/WrenAI/tree/main/sdk/wren-pydantic): `WrenToolkit.from_project(path)` → tools `wren_query`, `wren_dry_plan`, `wren_list_models`, and with memory `wren_fetch_context`, `wren_recall_queries` ("similar past NL→SQL pairs as few-shot examples"), `wren_store_query`; `toolkit.instructions()` yields a system prompt; requires `pydantic-ai >= 1.0, < 2.0`.
- *Prompt layouts / skills*: `skills/` holds only a discovery stub (`wren/SKILL.md`, `index.json`, `install.sh`, `SKILLS.md`, `AUTHORING.md`); the guides ship inside the CLI (`wren skills get onboarding|enrich-context|genbi`, `wren ask --guided|--direct`) (https://github.com/Canner/WrenAI/tree/main/skills, https://raw.githubusercontent.com/Canner/WrenAI/main/skills/SKILLS.md). Context beyond schema: `instructions.md`, `queries.yml`, LanceDB memory (`wren memory index|store|recall|fetch`).

**Maturity.** 18,143 stars; `open_issues_count` 246 (web: 171 issues + 75 PRs); `pushed_at` 2026-11-10 (https://api.github.com/repos/Canner/WrenAI). Releases: wren-v0.18.0 2026-11-10, v0.17.1 10-30, v0.17.0 10-27, wren-core-py-v0.8.2 10-23 — weekly-to-biweekly (https://api.github.com/repos/Canner/WrenAI/releases?per_page=6). Accuracy evidence: none published in the repo (evals folder has no README; "golden eval runner" is listed under "What's next").

**License / commercial.** Path-based multi-license (https://raw.githubusercontent.com/Canner/WrenAI/main/LICENSE): Apache-2.0 for `core/**`, `sdk/**`, `skills/**`, `examples/**`, root; CC BY 4.0 for `docs/**`; AGPL-3.0 text "included in advance for future modules", currently mapped to no path; package manifests are authoritative for published artifacts; "Wren"/"WrenAI" names and logos are trademarked. Commercial (Wren AI Cloud / self-hosted Enterprise Plus): row/column-level security and users/groups, GenBI UI/dashboards/embedding/APIs, "Scenario AI harnesses", audit/SLA/VPC/air-gapped. OSS: MDL engine, governed text-to-SQL, MCP server, CLI, 22+ connectors.

**Technique that solves one of our problems.** Dry-plan validation (EXPLAIN through the semantic layer, no execution) plus `strict_mode` is exactly a deterministic SQL-validation gate; `wren_recall_queries` is verified-query reuse as few-shot.

**Integration complexity: 3/5.** Python 3.11 wheels, pydantic-ai ≥ 1.0 adapter, Apache. But the compiler is a Rust binary with its own MDL; adopting it means a second semantic model next to ours or a translator, and the RLS/CLS fields in MDL are compiled by the OSS engine while the user/group management is commercial. **Recommendation: Extract** — the MDL shape (relationship cardinality, cube/time-dimension vocabulary, RLS condition-in-model) as a design reference for `semantic_yaml.py`, and the dry-plan + strict-mode gate as behaviour to replicate with sqlglot/EXPLAIN over our own compiler; Wrap `wren-core-py` only if we need DataFusion dialect planning for non-Postgres sources. **Do not copy:** the LanceDB memory (we have `context.example_query` in Postgres), the CLI-resident skills (guidance bound to an installed package version), AGPL-reserved future modules.

## 3. vanna-ai/vanna

**Scope & architecture.** "Accurate Text-to-SQL Generation via LLMs using Agentic Retrieval". **Archived by the owner on 2026-03-29, read-only**; `pushed_at` 2026-02-02 (https://github.com/vanna-ai/vanna, https://api.github.com/repos/vanna-ai/vanna). 23,804 stars, `open_issues_count` 289 (web: 227 + 62 PRs). Last releases: v2.0.2 2026-02-02, v2.0.1 2025-11-20, v2.0.0 2025-11-19, v0.7.9 2025-04-10 (https://api.github.com/repos/vanna-ai/vanna/releases?per_page=6). Python badge "3.8+". Layout `src/vanna/{agents,capabilities,components,core,examples,integrations,legacy,servers,tools,utils,web_components}`; `core/` has `agent, audit, enhancer, enricher, evaluation, filter, lifecycle, llm, middleware, observability, recovery, storage, system_prompt, tool, user, workflow`; `legacy/` keeps 11 vector stores (azuresearch, chromadb, faiss, marqo, milvus, opensearch, oracle, pgvector, pinecone, qdrant, weaviate), 14 LLM clients and `vannadb`.

**Training store and generation loop (0.x, `src/vanna/legacy/base/base.py`).** `train(ddl=|documentation=|sql=)` writes three collections; `generate_sql()` calls `get_similar_question_sql`, `get_related_ddl`, `get_related_documentation`, builds `get_sql_prompt` (DDL+docs in system, question/SQL pairs as user/assistant turns), `submit_prompt`; an `intermediate_sql` marker lets the LLM run an exploratory query and re-prompt with `df.to_markdown()` only if `allow_llm_to_see_data=True`; `extract_sql` is a regex ladder (CREATE TABLE AS, WITH, SELECT, ```sql, ```); `is_sql_valid` = `sqlparse` type == SELECT and is not called anywhere; `ask()` runs SQL, `auto_train` stores the pair when `len(df) > 0`, Plotly code is LLM-generated with a heuristic fallback chart; `generate_rewritten_question` merges follow-ups (not wired into `ask`). **No retry/self-correction on SQL error** ("Couldn't run sql" and return).

**2.0 (`src/vanna/core/agent/agent.py`, `src/vanna/tools/run_sql.py`).** `Agent(llm, tool_registry, user_resolver, AgentConfig)`; loop `while tool_iterations < self.config.max_tool_iterations`; tool errors go back as a `role="tool"` message (`result.error or "Tool execution failed"`), retry is left to the LLM; `context_enrichers` run in sequence; `RunSqlTool` delegates to an injected `SqlRunner`, returns a CSV preview truncated to 1,000 characters plus a filename and tells the LLM to call `visualize_data`; no row-level security in the tool itself (must live in the runner). `LegacyVannaAdapter` exposes `search_saved_correct_tool_uses` (the old training data) and admin-only `save_question_tool_args` (https://raw.githubusercontent.com/vanna-ai/vanna/main/MIGRATION_GUIDE.md).

**License / commercial.** MIT, "Copyright (c) 2024 Vanna.AI" (https://raw.githubusercontent.com/vanna-ai/vanna/main/LICENSE). vanna.ai sells Vanna Core / Vanna Cloud / Enterprise with "optional hosted admin features": Access Control, Observability, Agent Memory (hosted vector DB), File System, Audit Logs, Data Retention; no prices shown (https://vanna.ai/). The web component is served from `img.vanna.ai`.

**Technique that solves one of our problems.** The three-collection training store and "successful run ⇒ store (question, SQL) ⇒ few-shot" is the same idea as our `context.example_query`; the useful detail is the retrieval split (DDL / docs / verified pairs retrieved separately with their own top-k) and the `allow_llm_to_see_data` gate on exploratory queries.

**Integration complexity: 2/5** to copy ideas, 4/5 to depend on (archived, Python 3.8 era, own agent framework overlapping pydantic-ai). **Recommendation: Reference** — the project is archived; take the separate-collection retrieval and the auto-train-on-verified-run policy as confirmation of our design, nothing more. **Do not copy:** regex `extract_sql`, unused `is_sql_valid`, LLM-written Plotly code executed with `exec`, the 1,000-character CSV preview as the LLM's only view of results.

## 4. sinaptik-ai/pandas-ai

**Scope & architecture.** 23,949 stars, `open_issues_count` 24 (web: 7 issues + 17 PRs); **`pushed_at` 2025-10-28** — no commits for over a year (https://api.github.com/repos/sinaptik-ai/pandas-ai). v3.0.0 released 2025-10-07 (after a long alpha/beta train: a20 10-01, a19 07-13, beta.17 04-14); notes: SQL connectors + "query validation", views, `SemanticLayerSchema`, Docker sandbox, LiteLLM wrapper, removal of connectors/pipelines/BambooLLM, env vars renamed `PANDASAI_*` → `PANDABI_*` (https://api.github.com/repos/sinaptik-ai/pandas-ai/releases?per_page=6). Python "3.8+ <=3.11" (README). Packages: `pandasai/{agent,cli,core,data_loader,dataframe,ee,helpers,llm,query_builders,sandbox,smart_dataframe,smart_datalake,vectorstores}`; `extensions/{connectors,llms,sandbox/docker,ee}`.

**Key modules.**
- Semantic layer: `pandasai/data_loader/semantic_layer_schema.py` — pydantic `SemanticLayerSchema{name, description, columns[{name,type,description,expression,alias}], source{type,path|connection,table}, view, transformations[{type,params}], relations[{name,from,to}], group_by, order_by, limit, destination, update_frequency}`; column `expression` validated as parseable SQL. `pandasai/query_builders/{base,sql,view,local}_query_builder.py`, `sql_parser.py`, `sql_transformation_manager.py` compile it (file list only; contents not fetched).
- Code safety: `pandasai/core/code_generation/code_validation.py` — the **only** check is an AST walk requiring a call to `execute_sql_query` (`ExecuteSQLQueryNotUsed`); `code_cleaning.py` — strips `plt.show()`, drops top-level `execute_sql_query`/skill defs, rewrites `.png` literals to a temp chart path, and `_replace_table_names` raises `MaliciousQueryError` for a table outside the allowed set; `code_execution/environment.py` — `get_environment()` injects only `pd`, `plt`, `np`, **no `__builtins__` restriction, no import hook, no RestrictedPython**; `code_executor.py` — plain `exec(code, env)`, requires a `result` dict. `safe_libs/restricted_base.py` from v2 is gone (404).
- Sandbox: `pandasai/sandbox/sandbox.py` (abstract `start/stop/transfer_file/_exec_code`, `_extract_sql_queries_from_code` finds string literals containing SELECT/WITH) and `extensions/sandbox/docker/pandasai_docker/docker_sandbox.py` — image `pandasai-sandbox` built on demand, `sleep infinity`, `network_disabled=True`, **no memory/CPU limits, no volumes**; code is compiled locally then run with `exec_run('python -c "…"')`; DataFrames enter as CSV via `put_archive` to `/tmp`; **SQL is executed on the host**, each result saved as CSV and shipped in, and the in-container `execute_sql_query` is a stub that `pd.read_csv`s the mapped file; result is the serialized stdout.
- DataFrame → LLM: `pandasai/helpers/dataframe_serializer.py` — `<table dialect="…" table_name="…" description="…" columns="<json>" dimensions="RxC">` + `df.head()` CSV; `MAX_COLUMN_TEXT_LENGTH = 200`; attribute values are not escaped (the `columns` JSON breaks the quoting).

**License / commercial.** MIT Expat for the tree except `pandasai/ee/` (own `pandasai/ee/LICENSE`: production use requires "a valid PandasAI Enterprise license for the correct number of user seats"; copying/modifying allowed for development and testing) and third-party components (https://raw.githubusercontent.com/sinaptik-ai/pandas-ai/main/LICENSE, https://raw.githubusercontent.com/sinaptik-ai/pandas-ai/main/pandasai/ee/LICENSE). `pandasai/ee/` currently shows `skills/` + LICENSE. Managed PandasAI Cloud and self-hosted Enterprise are advertised on the README.

**Technique that solves one of our problems.** The sandbox trick "SQL never runs inside the container; results are materialised to files and mounted in" is a good isolation boundary for our sandbox pod (DB credentials never enter the sandbox). The `<table …>` + head CSV + 200-char truncation serialization is a reasonable LLM-facing dataframe format.

**Integration complexity: 3/5** (MIT, pydantic, sqlglot-adjacent) but **maintenance risk is high** (stalled since 2025-10, Python ≤ 3.11 pin, own agent). **Recommendation: Extract** the host-side-SQL/result-file sandbox pattern and the dataframe serializer format; **Reject** as a dependency. **Do not copy:** `exec()` with unrestricted builtins as "safety", the single-check validator, a Docker sandbox without resource limits, the YAML semantic layer (ours is richer and already MetricFlow-shaped).

## 5. HKUSTDial/awesome-data-agents

800 stars, `pushed_at` 2026-11-08, no license field; companion papers "A Survey of Data Agents: Emerging Paradigm or Overstated Hype?" (arXiv 2510.23587) and "Data Agents: Levels, State of the Art, and Open Problems" (arXiv 2602.04261, SIGMOD 2026 tutorial 2026-06-03); KDD Cup 2026 "Data Agents for Complex Data Analysis" track launched 2026-03-28 (https://github.com/HKUSTDial/awesome-data-agents, https://api.github.com/repos/HKUSTDial/awesome-data-agents).

**Taxonomy (SAE J3016 analogue).** L0 manual (human solo operator); L1 assisted — answers single questions / emits code snippets, no environment perception, heavy human validation; L2 partial — perceives environment (data lake, interpreter, APIs), uses memory and tools inside human-built pipelines (human = orchestrator); L3 conditional — orchestrates its own pipelines across tasks under human supervision ("no complete L3 system exists yet; current efforts are Proto-L3"); L4 high — proactive monitoring, finds problems worth investigating, no supervision; L5 full — invents new methods, no human. Proto-L3 industry list: Databricks Assist. DS Agent, BigQuery, Snowflake Cortex, Bytedance Data Agent, JoyAgent, TabTab, Xata; academia: DeepEye (SIGMOD Demo 2026), DeepAnalyze (ICML 2026), AgenticData, EvoDS (KDD 2026), SiriusBI (VLDB 2025), Data Interpreter. L2 NL2SQL entries: MAC-SQL, ChatBI, CHASE-SQL, Alpha-SQL, OpenSearch-SQL, ReFoRCE, DeepEye-SQL, SQLConductor. By this scale our product is L2 with a governed/approval loop; "Proto-L3" is the dynamic-agent direction.

**Five most relevant benchmarks (published numbers only).**
1. **Spider 2.0** (arXiv 2411.07763; 632 enterprise workflow problems: Snow 547 on Snowflake, Lite 547 across BigQuery/Snowflake/SQLite, DBT 68 on DuckDB). Leaderboard (https://spider2-sql.github.io/, no per-entry dates shown): Snow #1 Genloop Sentinel Agent v2 Pro 96.70; Lite #1 Tianqiong Data Agent + GLM 5.2 76.23, DivSkill-SQL (Snowflake AI Research × UCSD) 73.13; DBT #1 SignalPilot 65.6, JetBrains Databao 60.29. Lite is the closest to "cold" enterprise text-to-SQL and is still < 80%.
2. **BIRD** (https://bird-bench.github.io/; 12,751 pairs, 95 DBs). Overall test EX: AskData (AT&T) 83.40 on 2026-09-26, GrainSQL 82.95, DataGallery (Huawei) 82.39; human 92.96. Mini-Dev (500) on 2026-10-28: GPT-6.1 Sol 87.27, Claude Opus 5.5 87.13, Claude Sonnet 5.5 84.20 — single-model, no pipeline. Note: these names are as the page lists them.
3. **BIRD-Interact** (arXiv 2510.05318, ICLR 2026 Oral; 600 Full / 300 Lite tasks with a user simulator and executable test cases; c-Interact = fixed protocol, a-Interact = agentic). Abstract: GPT-5 "8.67% in c-Interact and 17.00% in a-Interact"; news 2025-08-26: best LLM 16.33% success on Full. README "Normalized Reward" on Full: c-Interact Gemini-2.5-Pro 20.92, O3-Mini 20.27, Claude-Sonnet-4 18.35; a-Interact GPT-5 25.52, Claude-Sonnet-4 23.28 (https://github.com/bird-bench/BIRD-Interact). The leaderboard table on https://bird-interact.github.io/ did not render. This is the benchmark for our clarification/multi-turn loop: interaction, not SQL syntax, is where systems fail.
4. **DABstep** (arXiv 2506.23719, 30 Jun 2025; 450 tasks + 10 dev, easy/hard levels; CC BY 4.0 dataset). Abstract: best agent 14.55% on the hardest tasks. The HF leaderboard tables did not load; the page states the Validated leaderboard "is now closed to new entries" pending DABStep-v2 (https://adyen-dabstep.hf.space/). A search surfaced unvalidated 100% hard-level entries (2026-05) and DS-STAR 45.24 hard — **not published/validated**, listed here only to flag that unvalidated numbers exist.

Runner-ups: **DAComp** (arXiv 2512.04324, ICLR 2026; 210 tasks; DE success "under 20%", DA scores "below 40%"), **DataSpace** (arXiv 2608.03451, 2026-08-04; 410 tasks, 7,439 artifacts; best 66.34%; harness choice alone moved results 15.36 points — relevant to our N-version voting).
